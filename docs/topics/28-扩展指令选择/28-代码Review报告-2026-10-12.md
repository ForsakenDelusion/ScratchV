### R1：LLVM 对新接入的 i32 输入给出假成功

**变更位置：**[dsl_parser.py](../../../scratchv/frontend/dsl_parser.py#L170) 的 typed `const`；[builder.py](../../../scratchv/ir/builder.py#L105) 的结果类型传播；[onnx_parser.py](../../../scratchv/frontend/onnx_parser.py#L182) 的 Add/Mul 统一交给 IR 优化器处理。未同步适配的消费者是 [llvm_codegen.py](../../../scratchv/backend/llvm_codegen.py#L221) 的四则运算和第 270 行 `_emit_load_const`。

复现输入：

```text
a = const(7,dtype:i32)
b = const(3,dtype:i32)
r = add(a,b)
return r
```

使用 `CompilerConfig(backend="llvm", optimize_level=...)`，不启用 `use_extended_isel`。`none/basic/all` 三种级别均返回 `success=True`、空错误列表，却分别输出如下语句：

```llvm
; none
%v_1_1 = fadd i32 7, 0.0
; basic / all
%v_3_1 = fadd i32 10, 0.0
```

`llvmlite.binding.parse_assembly(...).verify()` 直接失败：`floating point constant invalid for type`。`fadd` 只接受浮点或浮点向量类型，不能用来构造 i32 常量或做整数加法。[LLVM fadd 合同](https://llvm.org/docs/LangRef.html#fadd-instruction)

**为什么属于本次变更的集成问题：**前端已对所有后端开放新 `const` 语法，而编译入口的 extended-op 拒绝集合只有 `rem/min/max/abs/sqrt`，不会阻止 i32 const/add 进入 LLVM。`--extended-isel` 与 LLVM 互斥只约束选择器开关，不能保护已经共享的前端和 IR 变化。

还构造了经 `onnx.checker.check_model` 验证的、两个 INT32 标量 initializer 相加的 ONNX 模型。同一模型在基线 `f3af99d` 的 `basic/all` 下可通过 LLVM 解析，在 HEAD 下全部失败。需要准确区分：**基线 `none` 已存在此类非法整数常量发射问题；基线优化后通过解析，也不表示其 ONNX 返回类型语义完全正确。** 本次移除前端宿主折叠后，将这一未适配的后端问题扩展到了原来可输出合法 LLVM 文本的默认优化路径。

| 同一合法 ONNX INT32 Add 模型 | 基线 LLVM 解析 | HEAD LLVM 解析 | 两者 CompilerDriver 返回值 |
|---|---|---|---|
| none | 失败 | 失败 | 均 success=True |
| basic | 通过 | 失败 | 均 success=True |
| all | 通过 | 失败 | 均 success=True |

**影响：**调用者拿到“成功”的 `.ll`，到下游工具才失败。不是新增 RISC-V 指令是否正确的问题，而是共享前端改变后消费者未同步。

**建议修复：**按 dtype 发射 LLVM 整数常量和 `add/sub/mul`；整数除法另外处理目标语义。若 LLVM 暂不支持这些类型，应在 codegen 前明确拒绝并返回失败。不能把 IRBuilder 的类型传播改回 f32，也不能恢复不带 RV32 语义的前端折叠来掩盖问题。如果把 RV32 的除零/溢出合同沿用到 LLVM，不能简单用裸 `sdiv`，因为其对应边界是未定义行为。[LLVM sdiv 合同](https://llvm.org/docs/LangRef.html#sdiv-instruction)

**补测：**typed DSL 与 checker 合法的 ONNX INT32 输入，对 LLVM 输出执行解析/验证；覆盖 `none/basic/all`。只检查文本中有 `define` 或 `fadd` 不足以捕获这个问题。

**我们的解决方案（2026-10-12）：**按课题28的 RISC-V 交付范围，采用“LLVM 对未支持的操作与类型组合明确拒绝”的修复方案。原始课题没有要求扩展 LLVM 的完整整数支持；本次修复处理共享前端/IR 变更引起的假成功，不把 LLVM 整数后端或 RV32 除法语义移植追加为课题功能。

- [compiler.py](../../../scratchv/compiler.py) 在解析完成、运行优化器之前调用 LLVM 类型能力检查。`load_const/add/sub/mul/div/neg` 的现有 LLVM 发射只支持 f32/f64；遇到 i32/i64 时返回 `success=False`，错误包含操作、类型、函数和基本块。检查位于优化前，避免未使用的整数常量或可折叠运算被删除后绕过拒绝边界，`none/basic/all` 使用同一政策。
- [llvm_codegen.py](../../../scratchv/backend/llvm_codegen.py) 在 `emit()` 开始时复用同一检查，保护绕过 CompilerDriver 的调用，并检查优化后的 IR。`save()` 先生成完整文本，再打开目标文件，拒绝输入时不创建或截断文件。CompilerDriver 的拒绝也发生在输出写入之前。

### R2：多个函数合法重名，导致槽覆盖或类型冲突

**变更位置：**[inst_select_ext.py](../../../scratchv/backend/inst_select_ext.py#L245) 第 252–254 行；[allocation.py](../../../scratchv/backend/allocation.py#L71) 的 `collect_register_types`。前者以纯值名作为整个程序的 local_slots 字典键；后者也以纯值名对平铺机器流做类型归并。

最小结构是：分别使用两个 IRBuilder 建立 `f0`、`f1`，每个函数都 `alloca(1)`、store 常量、load、return，然后把两个 Function 放入同一个 Program。两个函数各自生成 `v_1/v_2/v_3`。`verify_ir(program)` 返回 `(True, [])`；函数内 SSA 值名相同是合法的。

| 函数类型 | 预期 | 实测：naive / greedy / linear |
|---|---|---|
| `f0:f64`、`f1:f64` | 两个函数各自有自己的局部槽 | 均失败：`local access has no layout entry: -8` |
| `f0:f64`、`f1:f32` | 同名值属于不同函数，可有不同精度 | 均失败：`virtual register v_2 has conflicting width or class` |

**根因：**`local_bytes` 跨函数累计，第一次 alloca 为 `-8`，第二次为 `-16`；两个槽同名 `v_1`，第二个覆盖第一个字典项，发射的第一处 `-8` 地址因此失去布局元数据。混合精度时，类型收集更早把两个函数的 `v_2` 当作同一虚拟寄存器并报冲突。

现有多函数测试使用同一个 IRBuilder，计数器持续递增；spill-only 测试显式把函数名加到值名前。这些输入绕开了函数内重名，不能证明实现真的按函数隔离。

**影响：**合法多函数 IR 被拒绝；目前 DSL/ONNX 单函数入口通常不触发。报告不把这描述成所有单函数编译均损坏。

**建议修复：**在平铺前把虚拟寄存器和局部对象按函数命名空间归一化，或者真正逐函数分配/布局后再拼接。键可用 `(function_id, value_name)`。只对 local_slots 换键仍不够，类型表、spill 表和分配器的值身份也需要保持相同作用域。

**补测：**分别建函数后合并，故意复用所有内部值名；既测同精度也测不同精度，并在修复后分别执行两个函数。这与当前已有的“多函数栈帧累计超过 2032 字节”测试属于不同边界。

**我们的解决方案（2026-10-12）：**先新增 [test_topic28_function_scope.py](../../../tests/test_topic28_function_scope.py) 的 20 项单元及执行回归，再修改生产代码。修复前为 **19 failed、1 passed**，失败包含局部槽记录覆盖、浮点位宽冲突和 naive spill 身份混用；重复选择的稳定性测试原本通过，单独保留用于约束修复后的命名行为。

- [instruction_select.py](../../../scratchv/backend/instruction_select.py) 在每个函数完成选择后、交给平铺机器管线之前，将该函数所有虚拟寄存器的定义及使用映射为唯一的后端名称。映射同时覆盖源 IR 值、参数/全局常量的函数内物化和选择器临时值，保留寄存器类别、位宽及物理寄存器/符号信息。名称通过已有临时名分配接口生成，避开所有源名称和已生成名称；仅多函数程序执行此步骤，单函数命名保持原有行为。
- [inst_select_ext.py](../../../scratchv/backend/inst_select_ext.py) 使用同一映射同步更新局部对象的 `local_slots` 键，并在开始处理下一个函数前完成更新。这样，后续函数再次使用 `v_1` 时不会覆盖前一个函数的局部槽。类型表、寄存器映射、spill 表和活跃性分析接收同一套唯一值身份，保留现有类型冲突检查。
- 保留程序级唯一的临时栈偏移，由既有 ABI finalizer 按函数压缩和重排实际栈帧；无需把所有函数的局部空间强行放进一个运行时栈帧，也不要求调用者把函数内 IR 名称改成全程序唯一。重命名仅作用于机器操作数，原始 IR 不被修改；同一个 selector 重复运行得到稳定的名称和槽记录。
- 单元测试覆盖 f64/f64、f64/f32 的值及局部槽隔离、FPR 位宽保留、naive spill 身份、与编译器名称相似的源值名、原始 IR 保留、重复选择以及基础整数选择器。执行测试覆盖两种精度组合 × 三种分配器 × 简单局部对象/16 个同时存活浮点值的寄存器压力；压力用例明确检查发生 spill，并独立汇编、链接后通过 QEMU 分别调用两个函数，检查返回位模式、fflags 及调用后的栈/GPR 状态。

### R3：IR 参照执行器与产品对同一个常量解释不同

**变更位置：**[types.py](../../../scratchv/ir/types.py#L118) 新增 `Value.bit_pattern` 并声明其优先于宿主转换；[rv32_emulator.py](../../../scratchv/simulator/rv32_emulator.py#L470) 的 `_resolve` 和第 577 行 `_op_load_const` 仍只使用 const_value/attrs.value。

复现：

```python
b.ret(b.load_const(0.0, T.FLOAT32, bit_pattern=0x3f800000))
```

这一 IR 通过 verifier，按新增合同，`bit_pattern` 是权威编码，实际值应为 1.0。对 f64 使用 `0x3ff0000000000000` 同理。

| 精度 | 三种分配器真实 ELF 返回位 | IRTraceExecutor 返回位 |
|---|---|---|
| f32 | `0x3f800000`，即 1.0 | `0x00000000`，即 0.0 |
| f64 | `0x3ff0000000000000`，即 1.0 | `0x0000000000000000`，即 0.0 |

所有 QEMU 场景 `fflags=0`。因此问题涉及**普通数值**，并不能用“参照不模拟 fflags/舍入模式”来解释。

**影响：**使用 IRTraceExecutor 的值对照可能报错或掩盖错误；本次 QEMU 验收入口没有依赖它充当二进制 oracle，因此既有验收仍通过。

**建议修复：**两个入口都从权威位模式解码常量，使用 NumPy 对字节做 dtype view，避免再经 Python float 转换。LOAD_CONST attrs 和 Value 的编码优先级应与 selector 一致。对于不承诺精确模拟的运算继续保留现有“值参照”定位，不需要在本课题重写软件浮点单元。

**补测：**同时覆盖 `_op_load_const` 和 `_resolve`；显式编码与宿主值不同、符号零、NaN payload 是不同输入类别。有限数值例子可以防止把失败误归因于异常标志。

**我们的解决方案（2026-10-12）：**先新增 [test_ir_trace_constants.py](../../../tests/test_ir_trace_constants.py) 的常量表示单元测试，再修复 [rv32_emulator.py](../../../scratchv/simulator/rv32_emulator.py) 的两个读取入口。最终 55 项测试同时覆盖 f32/f64：普通有限数值、编码为零但宿主值非零、负零、quiet/signaling NaN payload，以及指令独有编码、Value 独有编码和两者一致时的返回路径。预期字节直接由整数编码生成，避免测试与生产解码器共用同一实现。

- 使用统一的常量解码函数，将编码保存为 NumPy uint32/uint64 数组，再用 `view` 解释为对应 f32/f64。结果为保持原始位模式的零维数组，不经过 Python float；没有显式编码时保留原有数值转换及 i32/f32/f64 行为。解码边界拒绝布尔值、非整数、超出位宽或用于整数 dtype 的浮点编码。

## 3. 哪些改动是必须的：先看端到端依赖

基线已经有 `DataType.FLOAT64`、若干 F/D MachineOp、整数 DIV 和一个扩展选择器。问题是它们没有形成可靠的生产路径：结果类型经常回到默认 f32；浮点操作数仍可能被整数分配器处理；f64 的常量、spill、ABI 与发射也没有贯通。**本次必要的工作是把已有名义支持变成真实可编译、可调用、可执行的支持，不是再添加一个 FLOAT64 枚举。**

```mermaid
flowchart LR
    A[DSL/ONNX保留dtype和常量编码] --> B[IR结果保留类型]
    B --> C[优化保持整数和浮点合同]
    C --> D[按ISA和dtype选择机器指令]
    D --> E[保留GPR/FPR和值宽度]
    E --> F[分类分配与4/8字节spill]
    F --> G[每函数栈帧和ABI]
    G --> H[合法汇编与真实执行验证]
```

每条依赖都可以构造删除后失败的例子：

| 如果撤掉的改动 | 直接后果 |
|---|---|
| IRBuilder 结果类型传播 | f64 add 的 dest 回到 f32，下一环节精度/指令不一致 |
| 常量位模式和合法常量池 | `-0.0`/NaN 编码可能变；`li.d` 无标准实现可供正常汇编 |
| FPR 类别及位置约束 | 浮点数据可能分到 t/s 整数寄存器，或比较结果错误分到 FPR |
| 按宽度 spill | f64 被 4 字节 sw/lw 截断，压力下低位结果看似正常却失去高位 |
| ABI 和局部槽合并布局 | spill 与局部内存或保存区重叠；返回时 sp/保存寄存器状态不正确 |
| 浮点优化保护 | 符号零、逐步舍入或 fflags 与执行程序不同 |
| 输入能力校验 | 未支持的浮点/张量进入旧整数近似路径，产生“成功”的错误结果 |

f32/f64 数据共享 FPR 寄存器文件，用 width 区分即可；不需要另外建立“FPR32 类”和“FPR64 类”。地址仍使用 RV32 GPR。F/D 访存和运算、较窄值在更宽浮点寄存器中的表示属于架构约束。[RISC-V F](https://raw.githubusercontent.com/riscv/riscv-isa-manual/main/src/unpriv/f-st-ext.adoc)、[RISC-V D](https://raw.githubusercontent.com/riscv/riscv-isa-manual/main/src/unpriv/d-st-ext.adoc)

本报告对“必要性”使用四种口径：

| 标记 | 意义 |
|---|---|
| **核心必需** | 直接满足原始算子/类型要求；撤掉会缺功能或产生错误代码 |
| **集成必需** | 原任务未逐个点名，但端到端正确运行或修复已暴露问题需要 |
| **合同必需** | 为本分支主动选择的更严格数值/输入合同服务；缩小合同才可缩减 |
| **可选配套** | 使用体验、观测或维护便利；不决定核心数值结果 |

“必须具有某种能力”不等于“必须保留当前每一行实现”。下面同时说明合理替代方式和可以精简的部分。

#### 必须保留的语义例子

#### 指令选择为什么需要替换，而不是在旧代码旁追加

旧整数 min 使用 `slt` 的 0/1 直接与差值做 AND，0/1 不是全位掩码。例如 `min(7,2)` 的旧序列得到 7。新实现先计算 `mask=0-cond`，得到 0 或 `0xffffffff`，再按位选择完整的输入。这是正确性修复，不能因为新序列有 5 条指令就认定它是多余改动。max 可以继续用正确的伪指令展开、分支或当前掩码序列；**必须正确选择整值，当前无分支方案不是唯一必要方案**。

旧 IR 中的整数常量可以直接变成 MachineOperand immediate，而 `add/sub/mul/div` 等需要寄存器源。`mul rd,7,3` 不能作为正常 RV32 汇编交给 Clang。新增统一 materialize helper 是真实硬件路径的必要修复；合法性修复增加静态指令数不等于性能回退。

浮点比较的目的寄存器是 GPR 布尔值，浮点数据本身仍在 FPR。`!=` 使用 feq 结果为零分支；`>`/`>=` 交换源后使用 flt/fle。无需发明不存在的浮点 branch 指令。这些映射合理。

`li.d` 被常量池 `.word/.quad + la + flw/fld` 代替，确保生成标准工具能处理的编码。保留 `-0.0` 和 NaN 时应按 `(dtype,bits)` 去重，不能按 Python 数值相等去重。对 f32 也可以用整数位物化加 `fmv.w.x` 等合法方案；使用常量池是统一、可靠的实现选择，而非唯一实现。

显式 `rne` 使目标运算不依赖调用者当前 frm；如果数值合同只写“遵循调用者舍入模式”，这段可以不同。但本分支明确承诺固定 RNE，因此舍入属性从 selector 到 rewrite/emitter 全程保留是**合同内必需**。[RISC-V F 舍入与状态](https://raw.githubusercontent.com/riscv/riscv-isa-manual/main/src/unpriv/f-st-ext.adoc)

以下例子解释为什么这些改动不能视为与 topic28 无关的“顺手重构”：

1. **i32 中间溢出。**`(2147483647+1)/2` 必须先得到 `-2147483648`，再除以 2；无界 Python 整数一路折叠会得到相反符号。仅在最后包一层 i32 无法修复中间步骤。
2. **f32 逐步舍入。**先 `16777216.0+1.0`，再减 `16777216.0`，f32 路径结果为 0；以宿主双精度连续折叠则可变成 1。
3. **IEEE 非整数恒等式。**`Inf*0` 不能改成 0；`x+0` 也不能一概消去符号零和 signaling NaN 的行为。
4. **未使用不等于无效果。**未使用的 `sqrt(-1)` 仍可设置 NV；在零次循环之外提前执行则增加了原程序没有的异常标志。此处可观察性来自本分支明确选择的 fflags 合同。[RISC-V F 浮点状态](https://raw.githubusercontent.com/riscv/riscv-isa-manual/main/src/unpriv/f-st-ext.adoc)
5. **旧融合没有合法消费者。**旧 pass 把 `a*b+acc` 变成三源 `ADD [acc,a,b]`，而 selector 消费前两源。对 `2*3+4`，这甚至会算成 `4+2`；继续保留该转换没有正确性依据。

保守程度仍可优化：FNEG/FABS 等符号操作通常不设置 fflags，未用结果无需全部视为 effectful；某些静态可证明的浮点折叠也可能安全。但这些属于以后精化副作用模型，**现在用保守规则保证合同合理，全部禁用也不是理论上唯一必要的实现**。

#### 可以更小但不能失去的工程边界

ABI 通过 `[regalloc:*]` 注释及正则重写字节偏移，是沿用旧管线的实现成本选择；有测试保护时可以作为当前实现，但需要把这些标记当结构协议保护。后续应让 StackSlotRef 在最终布局前一直保留结构化身份。**不能只把注释删掉当美化，否则当前生产布局会失效。**

`_record_allocation_stats` 重新调用 emitter 统计站点，与核心代码生成无关，可拆成独立观测改动。这些数值是 selected/allocated 阶段统计，不能把它们当最终 ABI/汇编 pass 后的完整动态成本。

单标量参数、三组目标、非张量形状、硬件 sqrt、固定 RNE，以及不启用 DAG/LLVM 的 extended selector 都是清晰的范围选择。若用户要求这些边界之外的能力，需要继续实现；当前不应据此要求把整个 RISC-V 后端一次扩展为通用框架。

## 7. 哪些不是原始任务的最低必需，可以简化或拆分

| 改动 | 能否缩减 | 缩减时必须满足的条件 |
|---|---|---|
| 全套 protobuf typed wire reader 及非常规字段回归 | 可单独拆提交/课题；不是普通有限数 f64 运算的最低前提 | 保留当前强合同就需要源编码通路；缩范围必须同步文档和验收，不可静默损失 sNaN/payload。 |
| 固定 RNE 和可观察 fflags 导致的全局浮点保守优化 | 可细化，不宜直接删 | 需要对每条变换证明精度、NaN/符号零、异常标志一致；原任务没要求完整软件浮点证明器。 |
| 统一使用浮点常量池 | 方案可替代 | 替代发射必须标准工具可汇编、按位正确、满足 f32 在 D 上表示要求。 |
| i32 max 无分支掩码序列 | 可换成正确 pseudo 展开或分支 | 保持全有符号范围正确；不能回到以差值符号/0-1 掩码错误选择的方案。 |
| allocation 统计、cycle estimator、beautifier 注释 | 可拆为工具配套 | 若仍开放这些工具组合，其输出必须识别 F/D，统计应明确阶段和模型范围。 |
| 五个 pass 类的 preserve_float_semantics 配置 | 可以改成统一 policy 接口 | 不要只保护 preset 而遗漏显式 `--passes`，也不要改一个 pass 后另一个仍破坏相同合同。 |
| 两份相同的 `_riscv_i32_rem` | 可以直接去重 | 提取进共享除法/余数参照模块，保持 dtype 与零除/溢出行为。 |
| 保留 MulAddFusion 注册壳和兼容属性 | 壳合理，部分无实际效果的 policy 分支可精简 | 不重新生成三源 ADD；保留 preset/显式 pass 名的兼容性。 |
| 552 行设计及轮次命名测试组织 | 可整理、建立实现映射 | 不丢数值合同和实际缺陷类别；设计草案不能冒充已实现接口。 |
| 新文件的 Python 版本适配 | 应与项目声明同步，属于兼容性债务 | `pyproject.toml`/CONTRIBUTING 写 3.8+，CI 用 3.12。实测 3.8 加载新 onnx_bits.py 在 `tuple[int,int]` 注解失败；基线的 asm_parser_for_beautifier 已有同类导入问题，所以不能全归因于 topic28。新增 target_features 还用了 removeprefix。要么补兼容，要么统一提高声明并验证。 |

所谓“不是最低必需”，不意味着应把已经验证的保护删掉。更合理的处理是保持生产正确性，减少重复实现、清晰划分合同和提交边界。

## 8. 建议的处理顺序与合并条件

1. **先处理 R1。**共享 typed 前端不能对 LLVM 产出假成功；明确支持或拒绝，加入真实 LLVM 输出验证。不要撤回 IR 类型传播。
2. **处理 R2。**虚拟值和局部对象按函数保持身份，三种分配器统一受益；避免只修字典覆盖而留下类型/分配身份冲突。
3. **处理 R3、R4。**参照执行器遵守权威位模式；空分配结果清状态。这两项修复范围较小，适合本分支完成。
4. **补充接口与限制说明。**记录 ExtendedInstructionSelector 构造参数迁移、设计 API 与实际 API 差异，以及标量点积示例的范围。
5. **修复后按相关缺陷先做针对验证，再执行现有全量回归。**R1 加 LLVM verifier；R2 真正执行各函数；R3 对照有限数值编码；R4 检查同一实例三轮状态。无需再对每个解析边界机械展开全部分配器/优化级别。

本次对必要性的最终判断是：**类型传播、真实 F/D 选择、分类分配、8 字节 spill、合法常量发射、ABI 接线和优化安全保护应保留。** 非常规 protobuf 支持、统计/美化、部分保守策略和完整 API 草案属于可以明确拆分或精化的扩展。原始 4 个确定问题中 R1/R2/R3 已修复，R4 仍需处理；全量回归通过不能替代对这些未覆盖合同的针对验证。
